# агенст.md — Инструкции по применению SDD подхода в проекте Plasma System

## 1. Введение

Данный документ описывает **System Design Document (SDD)** подход, принятый в проекте **Plasma System**.  
SDD — это структурированный метод проектирования, который обеспечивает:

- единообразие архитектуры;
- прозрачность принимаемых решений;
- лёгкость поддержки и масштабирования;
- чёткое разделение ответственности между компонентами.

Документ служит руководством для всех участников команды при разработке новых фич, рефакторинге и интеграции.  
Все решения, описанные здесь, уже реализованы в текущей кодовой базе (см. структуру `app_ballon`, `app_vacuum`, `_settings`).

## 2. Принципы SDD в проекте

### 2.1. Доменно-ориентированное проектирование (DDD)

- Каждое приложение (`app_ballon`, `app_vacuum`) представляет собой отдельный **домен**.
- Внутри домена выделяются:
  - **Модели** (`models.py`) — сущности БД (например, `BallonMass`).
  - **DTO** (`dto.py`) — объекты передачи данных (например, `DTOInput`, `BallonMassDTO`).
  - **Репозитории** (`repo.py`) — абстракция доступа к данным (например, `BallonMassRepository`, `DjangoSettingsRepository`).
  - **Юзкейсы** (`usecase.py`) — бизнес-логика (например, `baloon_calculate`, `CheckVacuumUseCase`).
  - **Представления** (`views.py`) — контроллеры (API и веб).
  - **Задачи** (`tasks.py`) — фоновые процессы (Celery).

### 2.2. Чистая архитектура (Clean Architecture)

Слои строго изолированы:

- **Презентационный слой** (views) — обрабатывает HTTP-запросы, валидирует входные данные, вызывает юзкейсы.  
  Пример: `app_ballon.views.app_ballon` вызывает `baloon_calculate`.
- **Слой бизнес-логики** (usecase) — содержит сценарии использования, не зависит от фреймворков.  
  Пример: `CheckVacuumUseCase` принимает репозиторий через конструктор и выполняет проверку.
- **Слой данных** (repo, models) — инкапсулирует работу с БД и внешними сервисами.  
  Пример: `BallonMassRepository.get_last_ballon_mass()` скрывает детали запроса к модели.

**Правило:** юзкейс **не должен** напрямую импортировать модели Django — только через репозиторий.

### 2.3. Инверсия зависимостей (DIP)

- Репозитории реализуют абстрактные интерфейсы (см. `VacuumSettingsRepository`).
- Юзкейсы получают зависимости через конструктор (внедрение зависимости).  
  Пример: `CheckVacuumUseCase(settings_repo: VacuumSettingsRepository)`.
- Это упрощает тестирование (моки) и замену реализаций (например, на чтение из БД или внешнего API).

### 2.4. Конфигурация через переменные окружения

Все настройки, которые могут меняться в зависимости от окружения (dev/prod), выносятся в `.env` и читаются через `django-decouple`.  
Примеры (из `settings.py`):

- `THROTTLE_ENABLED`, `THROTTLE_RATE`, `THROTTLE_EXEMPT_PATHS`
- `CELERY_BROKER_URL`, `CELERY_RESULT_BACKEND`
- `DEBUG`, `SECRET_KEY`

## 3. Процесс разработки с применением SDD

### 3.1. Анализ требований

- Задокументируйте функциональные требования в виде пользовательских историй или сценариев.
- Определите входные и выходные данные для каждого API-эндпоинта (см. Swagger-документацию, доступную по `/swagger/`).

### 3.2. Проектирование

1. **Архитектурная схема** — определите, какие компоненты взаимодействуют (например, клиент → Web/Gunicorn → Django → Redis (троттлинг/брокер) → Celery → БД).
2. **Модель данных** — опишите сущности и их связи (ER-диаграмма). Сейчас используется SQLite, но для продакшена рекомендуется PostgreSQL.
3. **API-контракт** — используйте **OpenAPI (Swagger)** для спецификации всех эндпоинтов.  
   - Все API-функции должны быть аннотированы `@swagger_auto_schema` (см. `app_ballon.views` и `app_vacuum.views`).
4. **Выбор технологий** — обоснуйте использование Redis, Celery, Gunicorn, Docker и т.д. (в проекте уже используется).

### 3.3. Реализация

- Пишите код в соответствии с **PEP 8** и принятыми в проекте соглашениями.
- Каждый новый юзкейс должен сопровождаться модульными тестами (см. раздел 4).
- **Не допускайте дублирования кода** — выносите общие утилиты в отдельные модули.
- При работе с асинхронными задачами (Celery) создавайте отдельные `tasks.py` внутри приложения.  
  Пример: `app_vacuum.tasks` содержит `check_vacuum_async`, `send_vacuum_alert_email`, `periodic_vacuum_check`.

### 3.4. Тестирование

- **Unit-тесты** — покрывают юзкейсы и репозитории (изолированно).  
  Используйте `unittest` или `pytest` (в проекте пока нет тестов, но они должны быть добавлены).
- **Интеграционные тесты** — проверяют взаимодействие с БД, Redis, внешними API.
- **Нагрузочное тестирование** — используйте `locustfile.py` для проверки RPS и работы троттлинга.  
  Запуск: `locust -f locustfile.py --host=http://127.0.0.1:8000`.
- **Тестирование троттлинга** — скрипт `test_throttle.py` отправляет параллельные запросы и проверяет статус 429.
- **CI/CD** — автоматизируйте запуск тестов при каждом коммите (GitHub Actions / GitLab CI).

### 3.5. Документирование

- Ведётся в двух форматах:
  - **Код** — комментарии, docstring, типизация.
  - **Внешняя документация** — этот файл (`агенст.md`) и файлы в `docs/`.
- Актуализируйте Swagger-документацию при изменении API.

### 3.6. Развертывание и мониторинг

- Используйте **Docker Compose** для локальной разработки (`docker-compose.dev.yml`) и продакшена (`docker-compose.prod.yml`).
- Для продакшена:
  - Количество воркеров Gunicorn настраивается под нагрузку (`--workers 17` в dev, `--workers 3` в prod — корректируйте по необходимости).
  - Celery-воркеры и бит запускаются отдельными сервисами.
  - Используйте **Flower** для мониторинга задач (доступен на порту 5555).
- Логирование — все ошибки и предупреждения пишутся в стандартный вывод (контейнеры).  
  Используйте `logging.getLogger(__name__)` в middleware и других модулях.

## 4. Конкретные компоненты и их взаимодействие

### 4.1. ThrottleMiddleware (глобальный RPS-лимит)

- Реализован в `_settings/middleware.py`.
- Включается через `THROTTLE_ENABLED=True`.
- Лимит задаётся `THROTTLE_RATE` (запросов в секунду).
- Использует Redis для хранения счётчиков по IP и текущей секунде.
- Исключения для путей – `THROTTLE_EXEMPT_PATHS` (например, `/admin/`).
- При ошибке Redis работает в режиме fail‑open (запрос пропускается).

### 4.2. Celery и фоновая обработка

- Настройки в `settings.py`:
  - Брокер и бэкенд — Redis.
  - Используется `django_celery_beat` для периодических задач.
- Задачи:
  - `check_vacuum_async` — асинхронная проверка вакуума (вызывается из API `/vacuum/api/check_vacuum_async/`).
  - `send_vacuum_alert_email` — отправка уведомления при опасном статусе.
  - `periodic_vacuum_check` — периодическая задача, запускаемая по расписанию (добавляется через админку Django Celery Beat).
- Результат задачи можно получить по `task_id` через эндпоинт `/vacuum/api/task/<task_id>/`.

### 4.3. Репозитории и юзкейсы

- **app_ballon**:
  - `BallonMassRepository` — получение последней записи из БД.
  - `baloon_calculate` — оркестратор, использующий репозиторий и вспомогательные функции расчёта массы.
- **app_vacuum**:
  - `VacuumSettingsRepository` (интерфейс) и `DjangoSettingsRepository` (реализация) — получение порога из `settings.VACUUM_THRESHOLD`.
  - `CheckVacuumUseCase` — выполняет сравнение и возвращает структурированный ответ.

### 4.4. API-эндпоинты

| Путь | Метод | Описание |
|------|-------|----------|
| `/ballon/` | GET | Расчёт разрешения работ по газу (параметры: volume_liters, pressure_bar, temperature_Celsius) |
| `/vacuum/` | GET | Веб-страница проверки вакуума |
| `/vacuum/api/check_vacuum/` | GET | API проверки вакуума (синхронно) |
| `/vacuum/api/check_vacuum_async/` | POST | API запуска асинхронной проверки (возвращает task_id) |
| `/vacuum/api/task/<task_id>/` | GET | Получение результата асинхронной задачи |
| `/swagger/`, `/redoc/` | GET | Документация API |

## 5. Стандарты кодирования и лучшие практики

| Категория | Рекомендация |
|-----------|--------------|
| **Именование** | Классы — CamelCase, функции — snake_case, константы — UPPER_CASE. |
| **Типизация** | Обязательно используйте аннотации типов (Python 3.10+). |
| **DTO** | Все входные/выходные данные — через dataclass (см. `app_ballon.dto`). |
| **Обработка ошибок** | Перехватывайте исключения на уровне юзкейсов и возвращайте понятные HTTP-статусы (400, 429, 500). |
| **Работа с Redis** | Используйте пул соединений и обрабатывайте ошибки подключения (fail‑open). |
| **Celery** | Задачи должны быть идемпотентными, если это возможно. Настраивайте таймауты и повторные попытки. |
| **Безопасность** | Не храните секреты в коде, используйте `.env` и переменные окружения. |
| **Middleware** | Добавляйте новые middleware в `MIDDLEWARE` в правильном порядке (после аутентификации, перед views). |

## 7. Часто задаваемые вопросы (FAQ)

**Вопрос:** Как добавить новый эндпоинт с throttling?  
**Ответ:** Включите глобальный троттлинг через переменную `THROTTLE_ENABLED=True` и задайте лимит в `THROTTLE_RATE`. Для отдельных эндпоинтов можно использовать декоратор `@throttle_classes` с DRF-троттлами (уже используется в `app_ballon.views` и `app_vacuum.views`).

**Вопрос:** Как запустить Celery-воркера локально?  
**Ответ:** Выполните `celery -A _settings worker -l info` или используйте `docker-compose -f docker-compose.dev.yml up celery_worker`.

**Вопрос:** Где хранятся настройки для разных окружений?  
**Ответ:** В `.env` файле. Примеры значений описаны в `settings.py` через `config()`.

**Вопрос:** Как протестировать throttling?  
**Ответ:** Запустите `python test_throttle.py` или используйте Locust, чтобы эмулировать множество одновременных запросов. Ожидайте статус 429 при превышении лимита.

**Вопрос:** Как добавить новую периодическую задачу?  
**Ответ:** Зайдите в админку Django (`/admin/`), выберите `Periodic tasks` в разделе `Django Celery Beat` и создайте новую задачу с указанием интервала и задачи (например, `app_vacuum.tasks.periodic_vacuum_check`).

**Вопрос:** Почему при ошибке Redis запросы всё равно проходят?  
**Ответ:** Это реализовано как fail‑open (сбои в Redis не должны блокировать работу приложения). В middleware ошибка логируется, но запрос пропускается.
